# Подготовка к обсуждению работы

## Как кратко объяснить решение

Задача сведена к поиску по декларативной грамматике исторических агрегатов. Для каждого события признаки используют прошлые взаимодействия; бустинг предсказывает вероятность оценки 4–5. Поиск автоматически выбирает сущности и временные окна, проверяя предложения полноценным обучением модели. Кандидаты предлагаются случайно или по связи с остатками текущего бустинга. Сравнение отделяет качество исторических признаков, пользу отбора и вклад направляемой стратегии.

## Почему выбран MovieLens

Датасет содержит явный отклик, timestamp, пользовательские данные и многозначные жанры фильмов. Он позволяет реализовать причинно корректную историю и проверить пользовательско-жанровые связи на доступном CPU. Масштаб и механизм сбора оценок ограничивают перенос результатов на промышленный CTR. Следующий этап проверки — журнал показов и откликов с временем доступности метки.

## Где возможна утечка

Основные точки риска: агрегирование всего датасета перед split без причинного фильтра, включение текущей оценки, последовательный обход одновременных событий, выбор признаков по test и переобучение с early stopping на test. Реализация использует строгое условие `history.timestamp < query.timestamp`, атомарные границы split, независимые проверки против простого oracle и выбор моделей только по validation. Категории обрабатываются one-hot, исторические target-агрегаты задаются явно.

## Почему validation используется несколько раз

Validation является частью алгоритма выбора гиперпараметров и признаков. Многократный поиск создаёт риск переобучения на этом периоде. Test оценивает весь выбранный пайплайн на будущих событиях; два периода и три seed показывают его устойчивость. Дополнительные исследования используют те же тестовые периоды и обозначены как exploratory. Для последующего развития метода полезны nested temporal validation и отдельный новый датасет.

## Что означает корреляция с остатком

Остаток `y-p` показывает направление ошибки вероятностной модели. Большая абсолютная корреляция кандидата с остатками означает возможный дополнительный сигнал. Pearson-корреляция измеряет линейную связь; полноценное переобучение проверяет её полезность для CatBoost. Коррелированные окна и нелинейные взаимодействия объясняют, почему высокий proxy-score может дать слабое предложение.

## Какая автоматизация реализована

Алгоритм сам выбирает пакеты признаков и окна внутри заданной грамматики. Отдельный эксперимент начинает со статических признаков и строит историю предпочтений автоматически. Схема сущностей, агрегаты и пространство окон остаются исследовательскими решениями. Более широкая автоматизация может выводить сущности из схемы таблиц, адаптивно предлагать окна и учитывать вычислительную стоимость.

## Почему log loss и NDCG дают разные выводы

Log loss оценивает точность вероятностей на событиях; NDCG оценивает порядок кандидатов внутри пользователя. Пользовательские агрегаты могут улучшить оценку общей склонности к положительному отклику при небольшом изменении порядка фильмов. Ранжирование каталога на начале периода дополнительно меняет доступную историю и состав кандидатов. В работе обе постановки оцениваются отдельно.

## Что доказывает bootstrap

Парный bootstrap ресемплирует пользователей целиком и сравнивает модели на одинаковых событиях. Это учитывает кластерную зависимость оценок одного пользователя. Интервал относится к конкретному fold/seed и наблюдаемой популяции; несколько seed показывают другой источник вариативности. Временная зависимость между пользователями и повторное использование периода для дополнительных исследований остаются ограничениями.

## Как масштабировать решение

Для каждой сущности нужен отсортированный поток событий и состояния агрегатов по нескольким окнам. Текущий batch-пайплайн материализует все кандидаты; промышленная версия может сначала оценивать кандидатов на подвыборке и вычислять только предложенные пакеты. Состояния размещаются по ключам в распределённой системе, метки поступают по времени доступности, а feature plan версионируется вместе с моделью. Стоимость выбранного пакета должна входить в целевую функцию поиска.

## Что проверить перед отправкой

Выполнить короткий запуск на своей машине, прочитать основной отчёт и таблицы всех seed, разобраться в формулах каждого признака и самостоятельно объяснить изменения результатов при замороженной истории. Для защиты особенно полезно проследить одно событие через исходную таблицу, исторический агрегат, выбранный пакет и прогноз модели.

## Как объяснить развитие метода

Разработка на MovieLens 100K дала компактную модель с небольшим повышением log loss. Независимая когорта MovieLens 1M показала, что эта потеря усиливается на позднем тестовом горизонте и выходит за заранее заданный критерий. Следующий вариант автоматически добавляет полную историю той же сущности вместе с коротким окном и ограничивает число столбцов. Проверка другой когорты даёт log loss 0.537773 против 0.540127 ручного baseline и примерно на 43.3% меньше столбцов.

## Что именно подтверждено новой проверкой

Критерии компактности и приемлемой классификационной потери выполнены на ранее не оценённых пользовательских историях. Интервал средней по seed разности log loss с ручной моделью целиком отрицательный. Сравнение residual и random внутри парного алгоритма имеет интервал, включающий ноль. Это результат автоматического построения ограниченного набора; вклад отдельных изменений требует абляции на одной когорте, а каталоговая NDCG сохраняет свой компромисс.

## Почему важен отрицательный результат

Исходная гипотеза проверялась с заранее заданным допуском, и её отклонение опубликовано. Временная диагностика затем дала конкретное направление развития метода. Новая когорта разделяет разработку идеи и её оценку. Такая последовательность делает вывод проверяемым и позволяет обсуждать границы применимости.

## Учебный пример причинного агрегата

У фильма до запроса была одна оценка 5, полученная два дня назад. Для all-history item-пакета `count=1`, положительность `(1+2.5)/(1+5)=0.5833`, средняя оценка `(5+15)/(1+5)=3.3333`, gap=2 дня. Оценка текущего события добавляется после его timestamp. При другом событии с тем же timestamp история остаётся такой же; этим объясняется атомарная обработка одновременного feedback.

# Метод: поиск по грамматике с направлением по остаткам

## Представление признаков

Пакет определяется парой `(entity, window)`. Сущности: пользователь, фильм, пользователь–фильм, жанр, пользователь–жанр. Ручные окна: 7, 30, 90 дней и вся доступная история. Автоматически проверяемые окна: 1, 3, 10, 14, 21, 45, 60, 120, 180 дней. Получается 20 ручных и 45 дополнительных пакетов.

Для скалярной сущности пакет содержит `log(1 + count)`, сглаженную положительность `(positive_count + 2.5)/(count + 5)`, сглаженную среднюю оценку `(rating_sum + 15)/(count + 5)` и время с последнего события. Фиксированные априорные значения соответствуют вероятности 0.5 и оценке 3. Для пустой истории gap равен 3650 дням; наличие истории определяется count.

Жанровые пакеты агрегируют признаки по всем жанрам текущего фильма: среднее и максимум log-count, среднее и минимум положительности, среднее сглаженной оценки, минимальный gap. Среднее log-count представляет среднее логарифмов счётчиков жанров. Один исторический фильм может войти в несколько жанровых историй, поэтому итоговые счётчики имеют жанровую семантику.

Условие окна — `[timestamp - window, timestamp)`. Для каждого ключа сортируются события, вычисляются префиксные суммы rating/label; `searchsorted(..., side='left')` определяет обе границы. Даже при совпадающих timestamp текущая метка и все одновременные метки исключены.

## Направление поиска

1. Обучить CatBoost с ручными признаками и получить вероятности на validation.
2. Рассчитать остатки `r = y - p`.
3. Для каждого доступного пакета взять максимальную абсолютную Pearson-корреляцию его числовых признаков с остатками.
4. Предложить три ещё не проверенных пакета с максимальным скором.
5. Для каждого предложения обучить модель с текущими признаками и этим пакетом.
6. Принять лучший пакет при улучшении validation log loss минимум на 0.0001.
7. Повторить пять раундов, каждый раз обновляя остатки принятой модели.

Стратегия random использует ту же процедуру, предлагая три случайных пакета. Обе стратегии проверяют 15 моделей на fold/seed. Ранее проверенные пакеты повторно исключаются из предложений. Все 45 пакетов рассчитываются заранее одинаково для обеих стратегий. Постоянные на train признаки удаляются; пакет из одних констант исключается.

Корреляция с остатком — дешёвая эвристика потенциального дополнительного сигнала. Её преимущество оценивается экспериментально. Нелинейные взаимодействия признаков, коррелированные окна и случайные связи на validation могут ухудшить качество предложения. Проверка полноценным бустингом и независимый test ограничивают этот риск.

## Честность сравнения

Подбор ручного CatBoost: шесть заранее заданных сочетаний глубины, learning rate и L2-регуляризации; максимум 500 деревьев и early stopping 40. Гиперпараметры подбираются на первом seed каждого fold и далее фиксируются для всех методов этого fold. Число деревьев каждой модели выбирается на validation. Финальное обучение использует train+validation и выбранное число деревьев, сохраняя тот же seed.

Категориальные user/item/gender/occupation обрабатываются встроенным one-hot CatBoost с порогом 2000. Все категории MovieLens 100K попадают под этот порог. Это делает исходные категориальные признаки независимыми от target encoding; историческая информация задаётся явными причинными агрегатами. `has_time=True` сохраняет порядок обучения.

Бюджет уравнен по числу дорогих обучений. Реальное время зависит от числа признаков, числа деревьев и дополнительного скоринга; эти затраты сохраняются в JSON. Дополнительный контроль `all_packs` показывает эффект передачи бустингу всей грамматики без поиска.

## Масштабирование

Текущая реализация исследовательская: материализует матрицу всех кандидатов. Для N событий и P пакетов память растёт как O(NP), а вычисления включают сортировку для каждой сущности и запросы границ окна. Для миллиардов событий необходимы партиционирование по ключам, потоковые состояния или SQL/Spark, расчёт кандидатов по требованию и предварительный скоринг на подвыборке.

`FeaturePack.sql()` показывает эквивалент группировки и причинного фильтра. Производственная версия дополнительно учитывает время доступности feedback, задержки, версионирование метаданных и стоимость обслуживания выбранных пакетов.

# Повторная проверка и развитие исследования

## Исправления реализации

| Проблема | Исправление | Проверка |
| --- | --- | --- |
| Модели разных каталогов с одинаковым именем могли перезаписываться | Артефакты сохраняются внутри каждого запуска; новые запуски читают только собственные файлы | Тест разных путей и запрет подстановки старой модели |
| Проверки `assert` в аудите отключались при `python -O` | Критические проверки используют явные исключения | Пересчёт метрик полного эксперимента |
| Произвольный cutoff сохранял название `@10` | Названия NDCG/Recall соответствуют фактическому K | Численный тест `K=1` |
| Скалярные признаки предполагали порядок event_id | Результаты выравниваются по порядку запросов | Проверки всех пяти сущностей на перемешанных строках |
| Некорректные бюджеты и конфигурации обнаруживались поздно | Конфигурация проверяется перед загрузкой и обучением | Тесты ошибочных входов и готовых конфигураций |
| Незавершённый запуск мог перезаписываться | Новый запуск требует свежего каталога; продолжение проверяет provenance | Защитные условия CLI |
| Сериализация NumPy boolean останавливала публикацию критериев | Решения приводятся к JSON boolean | Регрессионный тест сериализации |
| Параллельные читатели могли увидеть частично записанный файл | Данные, feature cache и JSON записываются атомарно | Конкурентная запись и искусственное прерывание |
| Загруженный повреждённый архив попадал в cache | SHA-256 проверяется перед заменой файла | Проверка повторяемости после плохой загрузки |
| Поле времени provenance имело неоднозначную семантику | `captured_utc` обозначает момент фиксации; основной запуск сохраняет начало и завершение отдельно | Проверка provenance вне Git checkout |

Дополнительный сквозной тест изменяет будущие тестовые метки и подтверждает неизменность validation-прогнозов и выбора признаков. Первоначальные основные результаты после исправлений проходят повторный аудит: 252 значения метрик совпадают с сохранёнными предсказаниями.

## Статистическая проверка первоначального вывода

Усредняются индивидуальные потери по трём seed. Общие пользовательские bootstrap draws применяются ко всем периодам, сохраняя зависимость результатов одного пользователя между fold. На MovieLens 100K автоматическое построение с нуля повышает log loss на 0.001351 с 95%-интервалом [0.000352; 0.002384] и сокращает число столбцов с 108 до 52. Таким образом, наблюдается измеримый компромисс качества и компактности.

Дополнение ручного baseline даёт разность −0.000037 с интервалом [−0.000510; +0.000388]. Эти данные поддерживают малый средний эффект с существенной неопределённостью. Сравнение направляемого и случайного построения с нуля имеет разность −0.000829 с интервалом [−0.001807; +0.000236].

## Независимая проверка исходного метода

[Протокол MovieLens 1M](external_protocol.md) фиксируется до новых результатов. Когорта `user % 6 == 0` содержит 171 470 оценок 1006 пользователей. Ручной baseline получает средний log loss 0.551018, автоматическое построение — 0.558924 с 46 столбцами против 107. Разность +0.007906 имеет интервал [0.005027; 0.010794].

Критерий компактности выполнен. Верхняя граница потери превышает заранее установленный допуск 0.01, поэтому критерий приемлемого качества отклонён. Направляемый поиск превосходит случайный по средней потере: разность −0.002640, интервал [−0.004599; −0.000598]. Эти выводы относятся к фиксированным seed и тестовому периоду.

Диагностика времени обнаруживает усиление разницы после начала test. В первые семь дней автоматическая модель улучшает log loss примерно на 0.00111; после 90 дней разница повышается до +0.01662, после года — до +0.02737. Наблюдение согласуется с гипотезой о потере долгосрочной опоры при выборе коротких окон. Состав пользователей и распределение откликов также меняются; причинное объяснение требует дополнительных контролей.

## Новые исследовательские компоненты

Генератор горизонтов выводит окна из train-интервалов по сущностям, сохраняя независимость от меток и будущих событий. На MovieLens 100K получаются 12 и 14 кандидатов для двух fold. Все шесть запусков и горизонты опубликованы в [adaptive.json](../artifacts/full/adaptive.json); их статус — дополнительное исследование уже использованных тестовых периодов.

Следующий вариант автоматически объединяет выбранный горизонт с полной историей той же сущности и ограничивает число входных столбцов 60% ручного baseline. Его [протокол](paired_protocol.md) фиксируется до проверки ранее не оценённой когорты `user % 6 == 1`. Эта когорта содержит 172 119 оценок 1007 пользователей. Полные метрики, критерии и обсуждение переноса включаются в основной отчёт.

Сравнение разных когорт характеризует репликацию приемлемого качества, а прямой причинный вклад all-history объединения потребует отдельной абляции на одной когорте. Такая граница интерпретации сохраняется независимо от результата проверки.
